For the SimLab

What the Simulation and Data Lab Biology owns, inherits, and has to settle before BioPortal stops being a pilot.

Three things are blocked on people, not on code. No Helmholtz AAI client is registered, so nobody can sign in with a JSC account yet. OIDC_ALLOWED_ENTITLEMENTS is empty, which would accept any successful AAI login, including accounts outside the group this service is for. And DNS for bioportal.blablador.fz-juelich.de does not resolve, so no certificate can be issued and the ingress answers nothing. The first is an AAI review queue, the second is one environment variable, the third is one A record to 134.94.198.59.

Where this sits

The SimLab Biology exists to put HPC-bioscience work in front of Jülich's supercomputers and to support the groups that need it. BioPortal is the opposite end of that interface: the same models that normally require a submission script, an allocation and a GPU-scheduling conversation with a knowledgeable person, reachable by a biologist on a laptop who wants a structure and knows exactly nothing about SLURM.

That framing is what the service should be judged on, and it is also its limit. The portal is a convenience layer over one shared GPU queue. It is not an allocation of dedicated GPU time, it does not make a large design run affordable, and it does not replace support. Users who need to run 10,000 designs, or who need a parameter combination the portal does not offer, still need the SimLab — and the portal should send them there rather than quietly failing at them.

The two roles

Running BioPortal is two jobs that share a database and little else. One is operations: keep the pods up, the reconciler running, the certificate renewed, the patches applied, the artifact volume from silently filling, and answer the user who writes in with a job ID. The other is science support: decide which models are offered and which input paths are exposed, read the results well enough to say whether a surprising output is the model or the user, and take the decision to add the sixth model. Neither is a full-time role at the current volume, and the same person can hold both, but the second one cannot be delegated to whoever is on call — it is the part that needs the group's judgment.

Concretely, before anyone is announced as a user, and already noted in the internal open-items list:

  • a named service security contact, reachable during an incident, which Helmholtz AAI registration requires and Sirtfi assumes. SECURITY_CONTACT currently holds the institute's CERT address: a working mailbox, not a person who knows this service;
  • the privacy statement reviewed by the data protection officer. The listed DPO address was taken from published FZJ notices and has not been confirmed internally. PRIVACY_APPROVED stays 0 until that review happens, however complete the contact fields look;
  • the rules of use adopted by the institute, which is what TERMS_APPROVED claims. A page that marks itself a draft is honest; flipping that flag without the adoption makes it false;
  • who answers mail. Completion notifications go out under the portal's own address, and users will reply to them;
  • a decision on billing. The portal reports native gpu_seconds and no currency, because no rate was ever established. That is the right default, and it needs to be a decision rather than a leftover;
  • caps set on purpose. Five jobs per user against a global queue of about a hundred is a placeholder, not a policy. Both numbers shape who the service is usable by — a teaching session and a single postdoc want different answers.

Day one, in order

  1. Point DNS at the ingress — an A record for bioportal.blablador.fz-juelich.de to 134.94.198.59. Nothing else can be checked over TLS until this is done, and cert-manager issues the certificate only once the name resolves.
  2. Register the AAI client at the self-service, using the redirect URIs manage.py checkoidc prints. Admins review each request, so start early. A dev instance exists at login-dev.helmholtz.de if you want to rehearse the flow first.
  3. Put the credentials in the Secret — client ID, client secret, and CREDENTIAL_ENCRYPTION_KEY. Generate that key once. Rotating it makes every stored user key unreadable and every user must paste theirs in again, so it belongs in a password manager, not in anyone's shell history.
  4. Set OIDC_ALLOWED_ENTITLEMENTS to the group this service is for, and confirm with manage.py checkoidc that the configured endpoints still match the provider's discovery document. The endpoints cannot be guessed from the issuer URL.
  5. Run the model checks — manage.py livecheck --discover, then --queue. Both are free and both failing loudly is the best news you will get that day. Aliases and job acceptance are the two things that change under you.
  6. Submit one real job per model through the portal itself, with a normal user account rather than the admin, and follow it to the downloaded archive.
  7. Then flip the approval flags, announce, and expect the first week's mail to be about API keys rather than about science.

Announce it where the groups already read: a line in the SimLab's own news or the JSC mailing list reaches the people this is built for, and a portal nobody knows exists is a portal nobody uses. The /queue/ page and the admin's Trouble column are how you will know whether the caps are right.

What the portal promises, and what it must never start promising

The design decisions a new operator is most likely to undo by accident:

  • No progress bar, no ETA, ever. The service does not compute either, so the portal shows queue position, the reported stage and the waiting reason, and says outright that there is no estimate. A test fails if a percentage appears. A spinner added "just for feel" would be the first lie in the product.
  • A finished job is not a sound result. The plausibility check measures backbone bond lengths, which chemistry fixes near 3.8 Å. It catches outputs that are certainly broken; passing it says nothing about whether a prediction is right. Do not let anyone turn it into a green "valid" badge.
  • Transient HTTP failures never fail a job. Status is left alone, and the user is told the computation is unaffected. The one exception is a 404, which means the job is genuinely gone.
  • Each user brings their own Blablador key. GPU time meters to them, and the key is encrypted at rest, shown back only as a fingerprint, and never logged. Accepting an uploaded key by email, or sitting at someone's terminal to enter it for them, breaks that.
  • Cancellation is a race, and closing the tab is not a cancellation. A running job can still complete after being cancelled, so the wording says so.
  • Sequences, structures and request bodies are never logged. Problem reports arrive with job IDs, not inputs. Keep it that way when adding a model: a debug print of the parameters is a data leak with a plausible excuse.

Adding the sixth model

One module under jobs/specs/: a form, and a build(cleaned) returning the shim's parameters object. Register a ModelSpec with the exact alias from GET /v1/models, list the module in load_specs(), and the homepage, queue view, result page and this documentation site all pick it up. The value the group adds is in two fields the code cannot invent: caveats — what a scientist must know before spending GPU time — and result_note, what is actually in the archive.

The known-unvalidated paths are listed on the Running the portal page in docs/, along with the checks that precede exposing one. Treat that list as the group's own record of what has been proven to work.

Handing it over

Everything needed to run the deployment is in the repository: the README for the protocol and the traps, the Running the portal page in docs/ for the settings that matter, the env example for every variable, and the admin for the job trail. What is not in the repository is the operational state — open items, current flags, what is blocked on whom — which lives in a gitignored note next to the code. Copy that note somewhere the group will find it before the person who wrote it leaves, and add to it the moment something is decided, because the code will outlive the memory of why the caps are five and a hundred.
