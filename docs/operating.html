Running the portal

How the deployment fits together, and what to change when it needs tuning.

Two processes

A web process (gunicorn bioportal.wsgi) and exactly one reconciler (manage.py reconcile --loop). The web process never waits on the molecular service: it records the job and returns. The reconciler retries ambiguous submissions, polls each job on the schedule the service asks for, downloads finished archives, and sends completion mail.

Configuration

SettingWhy it matters
CREDENTIAL_ENCRYPTION_KEYFernet key used to encrypt each user's stored Blablador key. Lives in the environment, never in the database, and must be identical for the web and reconciler processes. Rotating it makes every stored credential unreadable.
ARTIFACT_ROOTWhere result archives are copied. This is what makes results outlive the service's 48-hour retention — size it for your throughput.
MAX_ACTIVE_JOBS_PER_USERPer-user fairness. The whole service accepts about 100 queued jobs and has a limited number of GPU slots, so set this deliberately before opening the portal up.
STALE_RUNNING_SECONDSHow long a job may sit in running before it is flagged. Flagged jobs are never auto-failed: a lost worker cannot be distinguished from a slow job.
OIDC_ALLOWED_ENTITLEMENTSRestricts sign-in to your group. Empty accepts any successful Helmholtz AAI login — fine for a pilot, tighten before announcing.

The admin

/admin/ lists every job with its event trail. The Trouble column flags jobs that are stale or that the portal cannot reach. Two actions are available: re-send a completion email, and retry an archive download — the latter only helps inside the 48-hour window.

Adding a model

Add a module under jobs/specs/ with a form and a build(cleaned) that returns the service's parameters object, register a ModelSpec with the alias from GET /v1/models, and list the module in load_specs(). The homepage, job list, queue view and these docs all pick it up automatically.
